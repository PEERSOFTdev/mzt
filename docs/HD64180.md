# HD64180 (Z180) disassembly support

Development notes for the work that added Hitachi HD64180/Z180 disassembly
support to `mdz80`. This is a history/design record, not end-user
documentation — see `mdz80/manual.html` for that, and `mdz80 -?` for the
current option list.

## Overview

`mdz80` gained a `-1` CLI flag that switches it to HD64180/Z180 mode: it
recognizes the CPU's extra ED-prefixed instructions (`IN0`, `OUT0`, `MLT`,
`TST`, `TSTIO`, `SLP`, `OTIM`/`OTDM`/`OTIMR`/`OTDMR`) alongside the standard
Z80 instruction set, and uses HD64180 T-state counts for the `-c` cycle
summary. This was needed to disassemble EPROM images from HD64180-based
hardware, which is otherwise unreadable through a plain Z80 disassembler
wherever it uses those extra opcodes.

## Starting point

Before this work, the user had already added a `cputype` enum (`c_Z80`,
`c_64180`, `c_8080`) to replace the old boolean `d8080` flag, wired up the
`-1` CLI flag, and made a first attempt at the ED-table mnemonics (in
`mdz80/opcodes.h`) and a new `mdz80/opcodes_z180.c`/`.h` pair. Alongside that,
the user had hand-extracted a complete HD64180 opcode/T-state reference table
from `Z80HELP.LBR`, a CP/M-era help archive (`Z80HELP/z180.hlp`, by Cameron W.
Cotrill, 1988) — unpacked at `Z80HELP/` in this repo. **`Z80HELP.LBR` is not
part of MZT or the `napobear/mzt` GitHub mirror**; the user located it
independently and added it to this repo specifically as reference material
for this work, and its T-state data (IN0=12, OUT0=13, MLT=17, TST r=7,
TST (HL)=10, TST nn=9, TSTIO nn=12, SLP=8, etc.) turned out to already be
completely correct once cross-checked.

The draft did not compile. It was checkpointed as-is in commit `f6bd39e`
("WIP: draft HD64180 (Z180) support in mdz80") before any fixes, so the
starting state is preserved in history.

## Problems found

- **`opcodes.h` was dead code.** It was never `#include`d by any source file
  and never listed in `CMakeLists.txt`. The Z180 mnemonic edits made there
  had zero effect on the compiled binary — all the real, live Z80 tables
  (`mnemtbl`, `edtbl`, `edcode`, etc.) are actually defined directly inside
  `opcodes_z80.c`. Fixed by deleting `opcodes.h` (commit `625bbd6`).

- **`opcodes_z180.c` was never built.** It wasn't listed in
  `CMakeLists.txt`, so it had never actually been compiled. Worse, as
  written it redefined `mnemtbl`, `cbtbl`, `regtbl`, `ddcbtbl`, `dd1tbl`,
  `dd2tbl`, `edtbl`, `edcode`, `ddcode`, and all the `*cycles*` timing arrays
  under the exact same names already defined in `opcodes_z80.c` — adding it
  to the build as-is would have failed immediately with duplicate-symbol
  link errors. None of those tables actually differ between Z80 and the
  HD64180 except the ED-prefix decode-flags table and the timing tables.
  Fixed by adding it to `CMakeLists.txt` (commit `625bbd6`) and rewriting it
  to only carry the genuine deltas (commit `2927dee`).

- **Incomplete `d8080` → `cputype` migration.** `pass1.c` and `pass2.c`
  still referenced the removed `d8080` global — the tree did not compile at
  all. Fixed in commit `c610908`, replacing every site with an explicit
  `cputype == c_8080` check rather than a bare truthiness test (`c_64180 ==
  1` is also truthy, and a bare `if (cputype)` would have silently routed
  HD64180 output through the 8080 code path).

- **A real decode bug in `pass2.c`.** The `OPT_SPEC` handling for ED-prefixed
  instructions reassigned the shared local `k` (the opcode byte) to hold the
  ED *second* byte, then reused `k` afterwards to compute the instruction's
  total length via `opttbl[k]`. This was harmless for pristine Z80 purely by
  coincidence — every valid Z80 ED second byte (0x40-0xBB) happens to map to
  a zero-size-bits slot in `opttbl` — but several new HD64180 second bytes
  (the IN0/OUT0 opcodes, which land in 0x00-0x3F) do not, so decoding would
  have desynced for the rest of the file after the first HD64180 instruction.
  Fixed in commit `c610908` by introducing a separate `k2` for the ED second
  byte, so `k` keeps meaning "the opcode byte" throughout the function.

- **A related bug in `pass1.c`'s reference scanner.** It treated any
  `edcode` flag with bit 1 set as "has a 4-byte address operand"
  (`edcode[j] & 2`), reading `pgmmem[i+2]`/`[i+3]` as a program address to
  flag. The new 3-byte IN0/OUT0/TST nn/TSTIO nn flags also have that bit
  set, which would have fabricated bogus label references from their
  port/immediate operand bytes. Fixed in commit `c610908` by narrowing the
  test to `(edc[j] & 3) == 3`, which is equivalent on the existing flag set
  and correctly excludes the new ones.

- **A CLI ordering bug**, pre-existing but surfaced while testing this work:
  `-1`/`-8`'s output-file extension (`.180`/`.d80`) was only set correctly if
  the flag appeared *after* the positional filename on the command line —
  the opposite of the order `mdz80`'s own usage text documents
  (`mdz80 [options] <filename>`). Fixed in commit `342942b` by moving the
  extension decision to run once, after option parsing completes and both
  the base filename and `cputype` are known.

## Design decisions

- **Single, dense, mode-independent `edtbl`.** Rather than maintaining a
  second near-duplicate mnemonic table, `edtbl` in `opcodes_z80.c` was
  extended in place to be dense across the whole 0x00-0xBB range (filling
  its previously-unused 0x00-0x3F and 0x7C-0x9F slots with the HD64180
  mnemonics). This is safe because every lookup into `edtbl` is gated by an
  `edcode`/`ed1code` check first, and the pristine `edcode` stays zero at
  every HD64180-only slot — so Z80/8080 output is completely unaffected
  (verified byte-identical against upstream on a regression file, aside from
  the version string).
- **`opcodes_z180.c`/`.h` shrunk to only genuine deltas**: `ed1code[]` (the
  ED-prefix decode-flags table, since which extra opcodes are legal differs
  by CPU) and the T-state tables, renamed to avoid colliding with
  `opcodes_z80.c`'s tables of the same name (`cycles` → `cycles1`, `cycles2`
  → `cycles21`, `cbcycles` → `cb1cycles`, and so on for
  `dd`/`ed`/`fd`/`ddcb`/`fdcb`). The user's original T-state data was reused
  unchanged.
- **Three new `OPT_ED_*` operand-printing flags** in `mdz80.h`:
  `OPT_ED_IN0`, `OPT_ED_OUT0`, `OPT_ED_IMM` — for the HD64180 forms that need
  an operand printed beyond the mnemonic text (port address for IN0/OUT0,
  immediate byte for TST nn/TSTIO nn). `TST r`, `TST (HL)`, `MLT`, and `SLP`
  needed no new flag — their full text is self-contained in the `edtbl`
  entry, reusing the existing `OPT_ED_2` flag, matching how the existing
  `MLT` entries already worked.

## Verification performed

- A synthetic test binary covering `IN0 A,(nn)`, `OUT0 (nn),A`, `MLT BC`,
  `TST A`, `TST (HL)`, `TST nn`, `TSTIO nn`, `SLP`, `OTIM`, followed by
  ordinary Z80 instructions (`LD A,n` / `JP`), disassembled correctly with
  `-1` — correct mnemonics, correct operand order, and correct realignment
  of the trailing Z80 instructions (proving the `k`/`k2` fix works).
- The same bytes run through plain `mdz80` (no `-1`) still report as invalid
  `DEFB` pairs, exactly as a stock Z80 disassembler should.
- A broader Z80-only regression file (covering `LD`, `CALL`, `JP`,
  `SBC HL,DE`, `LDIR`, `NEG`, `RLD`, CB rotates/BIT, DD/FD indexed
  loads/arithmetic/CB opcodes, `IN`/`OUT`, `HALT`) disassembles
  **byte-identical** to an unmodified `mzt-master` build, aside from the
  version string — confirming zero regression in plain Z80/8080 output.
- Full clean rebuild from a fresh checkout compiles with no new warnings.

## Known limitations / TBD

- The `-c` cycle-summary flag turns out to be driven by an undocumented,
  pre-existing control-file mini-language (`readcyclefile()` /
  `cycle_in()`/`cycle_end()` in `mdz80.c`), not a simple boolean switch. The
  HD64180 timing tables (`cycles1`, `ed1cycles`, etc.) are correctly wired in
  for when that mechanism is active, but the mechanism itself predates this
  work, isn't documented anywhere in the repo, and wasn't exercised
  end-to-end as part of this effort.
- No automated test suite exists for `mdz80`; all verification above was
  manual (synthetic test binaries plus a diff against an upstream build).
- One dead-code curiosity noticed and simplified rather than investigated
  further: `pass2.c` had a `d8080 != 2` condition that appears to be leftover
  scaffolding for a never-implemented 8085 mode (`d8080` was never actually
  set to 2 anywhere). Simplified away in commit `c610908`; not believed to
  be a functional risk, just noted for anyone who runs across it in the
  diff.
